ELIZA

O diálogo acima é do ELIZA, um sistema inicial de processamento de linguagem natural que podia manter uma conversa limitada com um usuário imitando as respostas de um psicoterapeuta rogeriano (Weizenbaum, 1966). ELIZA é um programa surpreendentemente simples que usa correspondência de padrões em palavras para reconhecer frases como “I need X” e mudar as palavras em saídas adequadas como “What would it mean to you if you got X?”. A imitação da conversa humana por ELIZA, embora muito rudimentar pelos padrões modernos, foi notavelmente bem-sucedida: muitas pessoas que interagiram com ELIZA passaram a acreditar que ele realmente entendia elas. Como resultado, este trabalho levou os pesquisadores a pensar primeiramente sobre os impactos de chatbots em seus usuários (Weizenbaum, 1976).

tokenização

É claro que os chatbots modernos não usam a simples imitação baseada em padrões que ELIZA pioneirou. No entanto, a abordagem baseada em padrões para palavras instanciada em ELIZA ainda é relevante hoje no contexto da tokenização, a tarefa de separar ou tokenizar palavras e partes de palavras de um texto corrido. A tokenização, o primeiro passo no NLP moderno, inclui abordagens baseadas em padrões que remontam a ELIZA.

Para entender a tokenização, primeiro precisamos perguntar: O que é uma palavra? Um é uma palavra? E New York? A natureza das palavras é semelhante em diferentes idiomas? Alguns idiomas, como o vietnamita ou o cantonês, têm palavras muito curtas, enquanto outros, como o turco, têm palavras muito longas. Também precisamos pensar em como representar palavras em termos de caracteres. Apresentaremos Unicode, o sistema moderno para representar caracteres, e a codificação de texto UTF-8. E apresentaremos o morfema, a subparte significativa das palavras (como o morfema -er na palavra longer).

BPEexpressões regulares

A maneira padrão de tokenizar texto é usar os caracteres de entrada para nos guiar. Assim, uma vez que entendermos as possíveis subpartes das palavras, apresentaremos o algoritmo padrão Byte-Pair Encoding (BPE) que divide automaticamente o texto de entrada em tokens. Este algoritmo usa estatísticas simples de sequências de letras para induzir um vocabulário de tokens de subpalavras. Todos os sistemas de tokenização também dependem de expressões regulares como etapa de processamento. A expressão regular é uma linguagem para especificar e manipular formalmente strings de texto, uma ferramenta importante em todos os sistemas modernos de NLP. Apresentaremos expressões regulares e mostraremos exemplos de seu uso.

Finalmente, apresentaremos uma métrica chamada edit distance que mede o quão semelhantes são duas palavras ou strings com base no número de edições (inserções, exclusões, substituições) necessárias para mudar uma string na outra. A distância de edição desempenha um papel em NLP sempre que precisamos comparar duas palavras ou strings, por exemplo, na crucial métrica word error rate para reconhecimento de fala automático.

2.1 Palavras

Quantas palavras há na seguinte frase?

They picnicked by the pool, then lay back on the grass and looked at the stars. [em português: Eles fizeram um piquenique perto da piscina, depois deitaram na grama e olharam para as estrelas.]

Esta frase tem 16 palavras se não contarmos pontuação como palavras, 18 se contarmos a pontuação. Se tratamos ponto (“.”), vírgula (“,”), e assim por diante como palavras depende da tarefa. A pontuação é crítica para encontrar limites de coisas (vírgulas, pontos, dois-pontos) e para identificar alguns aspectos de significado (pontos de interrogação, pontos de exclamação, aspas). Grandes modelos de linguagem geralmente contam a pontuação como palavras separadas.

enunciado

A linguagem falada introduz outras complicações no que diz respeito à definição de palavras. E quanto a esta enunciação de uma conversa falada? ( Utterance é o termo linguístico técnico para o correlato falado de uma frase).

I do uh main- mainly business data processing [em português: Eu faço uh principal- principalmente processamento de dados de negócios]

disfluênciafragmentopausa preenchida

Esta enunciação tem dois tipos de disfluencies. A palavra interrompida main- é chamada de fragment. Palavras como uh e um são chamadas de fillers ou filled pauses. Devemos considerar estas como palavras? Novamente, depende da aplicação. Se estivermos construindo um sistema de transcrição de fala, podemos querer eventualmente remover as disfluências. Mas também às vezes mantemos as disfluências. Disfluências como uh ou um são na verdade úteis no reconhecimento de fala ao prever a próxima palavra, porque podem sinalizar que o falante está reiniciando a cláusula ou ideia, e assim para o reconhecimento de fala elas são tratadas como palavras regulares. Como pessoas diferentes usam disfluências diferentes, elas também podem ser uma pista para identificação de falantes. De fato, Clark e Fox Tree (2002) mostraram que uh e um têm significados diferentes em inglês. O que vocês acham que são?

Talvez o mais importante, ao pensar no que é uma palavra, precisamos distinguir duas maneiras de falar sobre palavras que serão úteis ao longo do livro. Vamos considerar uma frase. Se ignorarmos a pontuação, esta frase tem 16 palavras, mas apenas 14 palavras únicas (porque the ocorre 3 vezes).

They picnicked by the pool, then lay back on the grass and looked at the stars. [em português: Eles fizeram um piquenique perto da piscina, depois deitaram na grama e olharam para as estrelas.]

tipo de palavraocorrência de palavra

Chamamos o conjunto de palavras únicas em um corpus de tipos de palavras. Assim, a frase acima tem 14 tipos de palavras, e se o vocabulário de uma língua inteira (o conjunto de palavras possíveis na língua) é V, o número de tipos é o tamanho do vocabulário |V|. Chamamos ocorrências de palavras o número N de palavras correntes, então 16 no exemplo acima.1

Ainda temos decisões a tomar! Por exemplo, devemos considerar uma string capitalizada (como They) e uma não capitalizada (como they) como o mesmo tipo de palavra type? A resposta é que depende da tarefa! They e they podem ser agrupados como o mesmo tipo em algumas tarefas onde nos importamos menos com a formatação, enquanto para outras tarefas, a capitalização é um recurso útil e é mantida. Às vezes, mantemos duas versões de um determinado modelo de NLP, uma com capitalização e outra sem capitalização.

Até agora, temos falado sobre palavras orthographic words: palavras baseadas em nosso sistema de escrita em inglês. Mas existem muitas outras maneiras possíveis de definir palavras.

Por exemplo, embora ortograficamente I’m seja uma palavra, gramaticalmente ela funciona como duas palavras: o pronome sujeito I e o verbo ’m, abreviação de am.

hanzi

As distinções se tornam ainda mais difíceis de fazer quando começamos a pensar em outras línguas. Por exemplo, os sistemas de escrita de línguas como chinês, japonês e tailandês simplesmente não têm palavras ortográficas! Ou seja, eles não usam espaços para marcar potenciais limites de palavras. Em chinês, por exemplo, as palavras são compostas por caracteres (chamados hanzi em chinês). Cada caractere geralmente representa uma única unidade de significado (chamada de morpheme, introduzida abaixo) e é pronunciável como uma única sílaba. As palavras têm em média entre 1,5 e 1,9 caracteres de comprimento, dependendo de como você mede. Mas como o chinês não tem palavras ortográficas, decidir o que conta como uma palavra em chinês é complexo. Por exemplo, considere a seguinte frase:

(2.1)姚明进入总决赛 yáo míng jìn rù zǒng jué sài
“Yao Ming reaches the finals”

Como Chen et al. (2017b) apontam, isso poderia ser tratado como 3 palavras (uma definição de palavras chamada definição do 'Chinese Treebank', na qual nomes chineses (sobrenome seguido por nomes próprios) são tratados como uma única palavra):

(2.2)姚明 进入 总决赛
YaoMing reaches finals

Mas a mesma frase poderia ser tratada como 5 palavras (padrão 'Peking University'), na qual os nomes são separados em suas próprias unidades e alguns adjetivos aparecem como palavras distintas:

(2.3)姚 明 进入 总 决赛
Yao Ming reaches overall finals

Finalmente, é possível em chinês simplesmente ignorar as palavras e usar os caracteres como elementos básicos, tratando a frase como uma série de 7 caracteres, o que funciona muito bem para o chinês, já que os caracteres estão em um nível semântico razoável para a maioria das aplicações (Li et al., 2019):

(2.4)姚 明 进 入 总 决 赛
Yao Ming enter enter overall decision game

Mas esse método não funciona para japonês e tailandês, onde o caractere individual é uma unidade muito pequena.

Essas questões com a definição de palavras tornam difícil usar palavras como base para a tokenização de texto em NLP em diferentes idiomas.

palavras funcionaispalavras de conteúdo

Existem também variantes da lei, que capturam o fato de podermos distinguir aproximadamente duas classes de palavras. Uma são as palavras funcionais , as palavras gramaticais como as inglesas a e of, que tendem a não crescer indefinidamente (uma língua tende a ter um número fixo delas). A outra são as palavras de conteúdo : substantivos, adjetivos e verbos que tendem a ter significados sobre pessoas, lugares e eventos. Substantivos, e especialmente substantivos particulares como nomes e termos técnicos, tendem a crescer indefinidamente. Assim, modelos que são sensíveis a essa diferença entre palavras funcionais e palavras de conteúdo têm um valor de $\beta$ para a parte inicial do *corpus*, onde todas as palavras ainda estão aparecendo, e então um segundo $\beta$ depois, para quando apenas as palavras de conteúdo ainda estão aparecendo. A Fig. 2.2 mostra um exemplo de Tria et al. (2018) mostrando dois valores de $\beta$ (chamados $\gamma$ em sua figura) para a lei de Heaps calculada no *corpus* de livros Gutenberg.

O fato de as palavras crescerem sem fim leva a um problema para qualquer modelo computacional. Não importa quão grande seja nosso vocabulário, nunca teremos um vocabulário que capture todas as palavras possíveis que possam ocorrer! Isso significa que nosso modelo computacional verá constantemente palavras desconhecidas : palavras que ele nunca viu antes. Este é um grande problema para modelos de aprendizado de máquina.

Devido a esses dois problemas (primeiro, que muitas línguas não têm palavras ortográficas, e defini-las *post-hoc* é desafiador, e segundo, que o número de palavras cresce ilimitadamente), modelos de linguagem e outros modelos de NLP não tendem a usar palavras como sua unidade de processamento. Em vez disso, eles usam unidades menores chamadas subpalavras que podem ser recombinadas para modelar novas palavras que nosso modelo nunca viu antes. Para pensar em definir subpalavras, primeiro precisamos falar sobre unidades menores que palavras; morfemas e caracteres .

2.2 Morfemas: Partes de Palavras

morfologiamorfema

As palavras têm partes. No nível dos caracteres, isso é óbvio. A palavra cats é composta por quatro caracteres, ‘c’, ‘a’, ‘t’, ‘s’. Mas isso também é verdade em um nível mais sutil: as palavras têm componentes que por si mesmos têm significados coerentes. Esses componentes são chamados morfemas , e o estudo de morfemas é chamado morfologia . Um morfema é uma unidade mínima portadora de significado em uma língua. Assim, por exemplo, a palavra fox consiste em um morfema (o morfema fox) enquanto a palavra cats consiste em dois: o morfema cat e o morfema -s que indica plural.

Aqui está uma frase em inglês segmentada em morfemas com hífens:

(2.6)Doc work-ed care-ful-ly wash-ing the glass-es

Como mencionamos acima, em chinês, convenientemente, o sistema de escrita é configurado de modo que cada caractere descreva principalmente um morfema. Aqui está uma frase em chinês mandarim com cada caractere morfema glosado, seguido pela tradução:

(2.7)梅 干 菜 用 清 水 泡 软 ，捞 出 后 ，沥 干 plum dry vegetable use clear water soak soft , remove out after , drip dry 切 碎 chop fragment Soak the preserved vegetable in water until soft, remove, drain, and chop

raizafixo

Geralmente distinguimos duas classes amplas de morfemas: raízes —o morfema central da palavra, fornecendo o significado principal—e afixos —adicionando significados “adicionais” de vários tipos. No exemplo em inglês acima, para a palavra worked, work é uma raiz e -ed é um afixo; similarmente para glasses, glass é uma raiz e -es um afixo.

morfemas inflexionaismorfemas derivacionais

Os afixos em si se dividem em duas classes, ou mais corretamente um contínuo entre dois polos. Em uma extremidade, os morfemas flexionais são morfemas gramaticais que tendem a desempenhar um papel sintático, como marcar concordância. Por exemplo, o inglês possui o morfema flexional -s (ou -es) para marcar o plural em substantivos e o morfema flexional -ed para marcar o tempo passado em verbos. Os morfemas flexionais tendem a ser produtivos e frequentemente obrigatórios, e seus significados tendem a ser previsíveis. Os morfemas derivacionais são mais idiossincráticos em sua aplicação e significado. Geralmente, eles se aplicam apenas a uma subclasse específica de palavras e resultam em uma palavra de uma classe gramatical diferente da raiz, muitas vezes com um significado difícil de prever exatamente. No exemplo acima, a palavra care (um substantivo) pode ser combinada com o afixo derivacional -ful para produzir um adjetivo (careful), e outro afixo derivacional -ly para resultar em um advérbio (carefully).

clítico

Existe outra classe de morfemas: clíticos. Um clítico é um morfema que age sintaticamente como uma palavra, mas que é reduzido em forma e anexado (fonologicamente e às vezes ortograficamente) a outra palavra. Por exemplo, o morfema inglês ’ve na palavra I’ve é um clítico; ele tem o significado gramatical da palavra have, mas em forma não pode aparecer sozinho (você não pode ter apenas “’ve” sozinho em uma frase). O morfema possessivo inglês ’s na frase the teacher’s book é um clítico. O artigo definido francês l’ na palavra l’opéra é um clítico, assim como preposições em árabe como b ‘por/com’ e conjunções como w ‘e’.

tipologia morfológica

O estudo de como as línguas variam em sua morfologia, isto é, como as palavras se dividem em suas partes, é chamado de tipologia morfológica . Embora as morfologias das línguas possam diferir em muitas dimensões, duas dimensões são particularmente relevantes para a tokenização computacional de palavras.

isolante

A primeira dimensão é o número de morfemas por palavra. Em algumas línguas, como o vietnamita e, em menor grau, o cantonês, cada palavra em média tem pouco mais de um morfema. Chamamos as línguas nesta extremidade da escala de línguas isolantes ou línguas analíticas. Por exemplo, cada palavra na seguinte frase em cantonês tem um morfema (e uma sílaba):

Alternativamente, em línguas como o koryak, uma língua chukotko-kamchatkana falada na parte norte da península de Kamchatka na Rússia, uma única palavra pode ter muitos morfemas, correspondendo a uma frase inteira em inglês (Arkadiev, 2020; Kurebito, 2017). aglutinantefusão

A segunda dimensão é o grau em que os morfemas são facilmente segmentáveis, variando de línguas aglutinantes como o turco, em que os morfemas têm limites relativamente nítidos, a línguas de fusão como o russo, em que um único afixo pode fundir múltiplos morfemas, como -om na palavra stolom (mesa-SG-INSTR- DECL1), que funde as categorias morfológicas distintas instrumental, singular e primeira declinação.

O sufixo inglês -s em She reads the article é um exemplo de fusão, pois o sufixo significa tanto terceira pessoa do singular quanto tempo presente, e não há como dividir o significado em partes diferentes do -s.

Embora tenhamos falado de forma vaga sobre essas propriedades (analítica, polissintética, fusional, aglutinante) como se fossem propriedades das línguas, na verdade as línguas podem usar diferentes sistemas morfológicos, de modo que seria mais preciso falar sobre isso como tendências gerais.

Não obstante, o fato de os morfemas serem difíceis de definir, e que muitas línguas podem ter morfemas complexos que não são fáceis de decompor em partes, torna muito difícil usar morfemas como um padrão para tokenização translinguística.

2.3 Unicode

Unicode

Outra opção que poderíamos considerar para tokenização é o nível do caractere individual. Como representamos caracteres entre línguas e sistemas de escrita? O padrão Unicode é um método para representar texto escrito usando qualquer caractere em qualquer escrita das línguas do mundo (incluindo línguas mortas como cuneiforme sumério e línguas inventadas como Klingon).

Vamos começar com uma breve nota histórica sobre um subconjunto específico do Unicode para inglês (tecnicamente chamado de ‘Basic Latin’ no Unicode e comumente referido como ASCII). Começando na década de 1960, os caracteres latinos usados para escrever inglês (como os usados nesta frase) eram representados com um código chamado ASCII (American Standard Code for Information Interchange). O ASCII representava cada caractere com um único byte. Um byte pode representar 256 caracteres diferentes, mas o ASCII usava apenas 128 deles; o bit de ordem superior dos bytes ASCII é sempre definido como 0. (Na verdade, ele usava apenas 95 deles e o restante eram códigos de controle para uma máquina obsoleta chamada teletipo). 2.3.1 Pontos de Código

ponto de código

Como funciona? O Unicode atribui um ID exclusivo, chamado code point, para cada um desses 150.000 caracteres.

O code point é uma representação abstrata do caractere, e cada code point é representado por um número, tradicionalmente escrito em hexadecimal, de 0 até 0x10FFFF (que é 1.114.111 em decimal). Ter mais de um milhão de code points significa que há muito espaço para novos caracteres. É tradicional representar esses code points com o prefixo “U+” (que significa apenas “o seguinte é uma representação hexadecimal Unicode de um code point”). Assim, o code point para o caractere a é U+0061, que é o mesmo que 0x0061. (Note que o Unicode foi projetado para ser retrocompatível com o ASCII, o que significa que os primeiros 128 code points, incluindo o código para a, são idênticos ao ASCII.) Aqui estão alguns code points de exemplo; alguns (mas não todos) vêm com descrições:

glifo

Note que um ponto de código não especifica o glifo glifo, a representação visual de um caractere. Os glifos são armazenados em tipografias. O ponto de código U+0061 é uma representação abstrata de a. Pode haver um número indefinido de representações visuais, por exemplo em diferentes tipografias como Times Roman (a) ou Courier (a), ou diferentes estilos de fonte como negrito (a) ou itálico (a). Mas todos eles são representados pelo mesmo ponto de código U+0061.

2.3.2 Codificação UTF-8

Embora o ponto de código (o id único) seja a representação abstrata Unicode do caractere, nós não simplesmente colocamos esse id em um arquivo de texto.

codificação

Em vez disso, sempre que precisamos representar um caractere em uma string de texto, escrevemos uma codificação do caractere. Existem muitos métodos de codificação possíveis, mas o método de codificação chamado UTF-8 é de longe o mais frequente (por exemplo, quase toda a web é codificada em UTF-8).

Vamos falar sobre codificações. A representação Unicode da palavra hello consiste na seguinte sequência de 5 pontos de código:

U+0068 U+0065 U+006C U+006C U+006F

Podemos imaginar um método de codificação muito simples: apenas escrever o id do ponto de código em um arquivo. Como existem mais de 1 milhão de caracteres, 16 bits (2 bytes) não são suficientes, então precisaremos usar 4 bytes (32 bits) para capturar os 21 bits que precisamos para representar 1,1 milhão de caracteres. (Poderíamos caber em 3 bytes, mas é inconveniente usar múltiplos de 3 para bytes.)

Com essa representação de 4 bytes, a palavra hello seria codificada como o seguinte conjunto de bytes:

00 00 00 68 00 00 00 65 00 00 00 6C 00 00 00 6C 00 00 00 6F

Mas nós não usamos essa codificação (que é tecnicamente chamada UTF-32) porque torna cada arquivo 4 vezes maior do que seria em ASCII, tornando os arquivos realmente grandes e cheios de zeros. Além disso, esses zeros causam outro problema: descobre-se que ter qualquer byte que seja completamente zero atrapalha a compatibilidade com versões anteriores para sistemas baseados em ASCII que historicamente usavam um byte 0 como marcador de fim de string.

UTF-8codificação de comprimento variável

Em vez disso, o padrão de codificação mais comum é UTF-8 (Unicode Transformation Format 8), que representa os caracteres de forma eficiente (usando menos bytes em média) escrevendo alguns caracteres usando menos bytes e outros usando mais bytes. O UTF-8 é, portanto, uma codificação de comprimento variável.

Para alguns caracteres (os primeiros 128 pontos de código, ou seja, o conjunto de caracteres ASCII), o UTF-8 os codifica como um único byte, então a codificação UTF-8 de hello é:

68 65 6C 6C 6F

Isso significa convenientemente que arquivos codificados em ASCII também são codificações UTF-8 válidas!

Mas o UTF-8 é uma codificação de comprimento variável, o que significa que pontos de código ≥128 são codificados como uma sequência de dois, três ou quatro bytes. Cada um desses bytes está entre 128 e 255, então eles não serão confundidos com ASCII, e cada byte indica nos primeiros bits se é uma codificação de 2 bytes, 3 bytes ou 4 bytes. U+010000-U+10FFFF 000uuuuu zzzzyyyy yyxxxxxx 11110uuu 10uuzzzz 10yyyyyy 10xxxxxx

A Fig. 2.5 mostra como esse mapeamento ocorre. Por exemplo, essas regras explicam o que fazer com o caractere ñ, que tem ponto de código U+00F1. Olhamos na segunda linha porque U+00F1 está entre U+0080 e U+07FF. Em seguida, pegamos a sequência de bits correspondente a U+00F1 e a mapeamos nos valores y e x na segunda coluna. Neste caso, parece 00000000 11110001, (onde azul indica a sequência yyyyy e vermelho a sequência xxxxxx). Finalmente, o lado direito da tabela mostra como essa sequência de bits é codificada na sequência de bits de dois bytes 11000011 10110001, que corresponde a 0xC3B1. Como resultado dessas regras, os primeiros 127 caracteres (ASCII) são mapeados para um byte, a maioria dos caracteres em scripts europeus, do Oriente Médio e africanos mapeia para dois bytes, a maioria dos caracteres chineses, japoneses e coreanos mapeia para três bytes, e caracteres CJKV mais raros, emojis e alguns símbolos mapeiam para 4 bytes.

O UTF-8 tem várias vantagens. É relativamente eficiente, usando menos bytes para caracteres comumente encontrados, não usa bytes nulos (exceto ao representar literalmente o caractere NULL, que é U+0000), é retrocompatível com ASCII e é auto-sincronizante, o que significa que se um arquivo for corrompido, é sempre possível encontrar o início do próximo ou anterior caractere apenas movendo-se até 3 bytes para a esquerda ou direita. Unicode e Python: A partir do Python 3, todas as strings Python são armazenadas internamente como Unicode, cada string uma sequência de pontos de código Unicode. Assim, funções de string e expressões regulares se aplicam nativamente aos pontos de código. Por exemplo, funções como len() de uma string retornam seu comprimento em caracteres, ou seja, pontos de código, e não seu comprimento em bytes.

Ao ler ou escrever de um arquivo, no entanto, os pontos de código precisam ser codificados e decodificados usando um método como UTF-8. Ou seja, cada arquivo é codificado em alguma codificação. Se não for UTF-8, é um método de codificação mais antigo como ASCII ou Latin-1 (iso 8859 1). Não existe um arquivo de texto sem uma codificação. O método de codificação é especificado em Python ao abrir um arquivo para leitura e escrita.

2.4 Tokenização Subword: Byte-Pair Encoding

tokenizaçãotokens

Tokenização, a primeira etapa do processamento de linguagem natural, é o processo de segmentar o texto de entrada corrente em tokens.

Vimos três candidatos para tokens: palavras, morfemas e caracteres. Mas cada um tem problemas como unidade. Palavras e morfemas parecem estar aproximadamente no nível certo para o processamento de PLN, pois tendem a ter significados consistentes, mas são desafiadores de definir formalmente. Caracteres são mais fáceis de definir, mas parecem ser uma unidade muito pequena para escolher como tokens.

Nesta seção, introduzimos o que fazemos na prática para PLN: usar uma abordagem orientada a dados para definir tokens que geralmente resultarão em unidades do tamanho de morfemas ou palavras, mas ocasionalmente usar unidades tão pequenas quanto caracteres.

Por que tokenizar a entrada? Uma razão é que converter uma entrada em um conjunto fixo e determinístico de unidades significa que diferentes algoritmos e sistemas podem concordar em perguntas simples. Por exemplo, Quanto tempo tem este texto? (Quantas unidades ele tem?). Ou: don’t ou New York é um token ou dois? A padronização é, portanto, essencial para a replicabilidade em experimentos de PLN, e muitos algoritmos que introduzimos neste livro (como a métrica perplexity para modelos de linguagem) assumem que todos os textos têm uma tokenização fixa.

Algoritmos de tokenização que incluem tokens menores para morfemas e letras também eliminam o problema de palavras desconhecidas. Quais são esses? Como veremos no próximo capítulo, os algoritmos de NLP frequentemente aprendem alguns fatos sobre a linguagem a partir de um *corpus* (um *corpus* de treinamento) e, em seguida, usam esses fatos para tomar decisões sobre um *corpus* de teste separado e sua linguagem. Assim, se nosso *corpus* de treinamento contiver, digamos, as palavras low, new e newer, mas não lower, então, se a palavra lower aparecer em nosso *corpus* de teste, nosso sistema não saberá o que fazer com ela.

subpalavras

Para lidar com esse problema de palavra desconhecida, os *tokenizers* modernos induzem automaticamente conjuntos de *tokens* que incluem *tokens* menores que palavras, chamados subwords. *Subwords* podem ser substrings arbitrárias, ou podem ser unidades portadoras de significado como os morfemas -est ou -er. Em esquemas de tokenização modernos, muitos *tokens* são palavras, mas outros *tokens* são morfemas frequentemente ocorrentes ou outros *subwords* como -er. Cada palavra não vista pode, assim, ser representada por alguma sequência de unidades *subword* conhecidas. Por exemplo, se não tivéssemos visto a palavra lower, quando ela aparecer, poderíamos segmentá-la com sucesso em low e er, que já tínhamos visto. No pior caso, uma palavra realmente incomum (talvez um acrônimo como GRPO) pode ser tokenizada como uma sequência de letras individuais, se necessário.

BPE

Dois algoritmos de tokenização são amplamente utilizados em modelos de linguagem modernos: o byte-pair encoding (BPE) (Sennrich et al., 2016) e o unigram language modeling (ULM) (Kudo, 2018).$\text{2}$ Nesta seção, introduzimos o algoritmo byte-pair encoding ou BPE (Sennrich et al., 2016; Gage, 1994); veja a Fig. 2.6.

Como a maioria dos esquemas de tokenização, o algoritmo BPE tem duas partes: uma fase de treinamento e a fase de codificador. Em geral, na fase de treinamento de tokens, o tokenizer recebe um corpus de treinamento bruto (geralmente pré-separado em palavras, por exemplo, por espaço em branco) e induz um vocabulário, um conjunto de tokens. Em seguida, na fase de codificação, o tokenizer recebe uma frase de teste bruta e a codifica nos tokens do vocabulário que foram aprendidos no treinamento.

2.4.1 Treinamento BPE

O algoritmo de treinamento BPE mescla iterativamente *tokens* vizinhos frequentes para criar *tokens* cada vez mais longos. O algoritmo começa com um vocabulário que é apenas o conjunto de todos os caracteres individuais. Ele então examina o *corpus* de treinamento e encontra os dois caracteres que são mais frequentemente adjacentes. Imagine que nosso *corpus* original tem 10 caracteres de comprimento, usando um vocabulário de 5 caracteres, {A, B, C, D, E}:

A B D C A B E C A B

O par de caracteres vizinhos mais frequente é “A B”, então nós os mesclamos, adicionamos um novo *token* mesclado ‘AB’ ao vocabulário e substituímos cada ‘A’ ‘B’ adjacente no *corpus* pelo novo ‘AB’:

AB D C AB E C AB

Agora temos um vocabulário de 6 *tokens* possíveis {A, B, C, D, E, AB}, e o *corpus* tem comprimento 7. E agora o par de *tokens* mais frequente é “C AB”, então nós os mesclamos, levando a um vocabulário com 7 *tokens* {A, B, C, D, E, AB, CAB}, e o *corpus* tem comprimento 5.

AB D CAB E CAB

O algoritmo continua a contar e mesclar, criando novas sequências de caracteres cada vez mais longas, até que k mesclagens tenham sido feitas criando k *tokens* novos; k é, portanto, um parâmetro do algoritmo. O vocabulário resultante consiste no conjunto original de caracteres mais k novos símbolos. Esse é o cerne do algoritmo.

A única complicação adicional é que, na prática, em vez de rodar na sequência bruta de caracteres, o algoritmo geralmente é executado apenas dentro de palavras. Ou seja, o algoritmo não mescla através de limites de palavras. Para fazer isso, o corpus de entrada é frequentemente primeiro separado por espaços em branco e pontuação (usando as expressões regulares que definiremos mais adiante no capítulo). Isso fornece um conjunto inicial de strings, cada uma correspondendo aos caracteres de uma palavra, (com o espaço em branco geralmente anexado ao

início da palavra), juntamente com as contagens das palavras. Então, enquanto as contagens vêm de um corpus, as mesclagens são permitidas apenas dentro das strings.

2.4.2 Codificador BPE

Depois de aprendermos nosso vocabulário, ocodificador BPE é usado para tokenizar uma frase de teste. O codificador simplesmente executa nos dados de teste as mesclagens que aprendemos com os dados de treinamento. Ele as executa na ordem em que as aprendemos (ou seja, de forma gulosa, significando começando pelo mais frequente nos dados de treinamento). As frequências nos dados de teste não desempenham um papel, apenas as frequências nos dados de treinamento. Então, primeiro segmentamos cada palavra da frase de teste em caracteres. Em seguida, aplicamos a primeira regra: substituir cada instância de n e no corpus de teste por ne, e então a segunda regra: substituir cada instância de ne w no corpus de teste por new, e assim por diante. Ao final, muitos das mesclagens simplesmente recriaram palavras no conjunto de treinamento. Mas as mesclagens também criaram conhecimento de morfemas como o prefixo re- (que pode aparecer em talvez combinações não vistas como revisit ou rearrange), ou o morfema new sem um espaço inicial (portanto, interno à palavra) que pode aparecer no início das frases ou em palavras não vistas no treinamento como anew.

É claro que em cenários reais, o BPE é executado com dezenas de milhares de fusões em um *corpus* de entrada muito grande, para produzir tamanhos de vocabulário de 50.000, 100.000 ou até 200.000 *tokens*. O resultado é que a maioria das palavras pode ser representada como *tokens* únicos, e apenas as palavras mais raras (e palavras desconhecidas) terão que ser representadas por múltiplos *tokens*. Pelo menos para o inglês. Para sistemas multilíngues, os *tokens* podem ser dominados pelo inglês, deixando menos *tokens* para outros idiomas, como discutiremos abaixo.

2.4.3 BPE na prática

O exemplo acima apenas mostrou o aprendizado simples de BPE a partir de sequências de bytes ASCII. Como o BPE funciona com entrada Unicode? Normalmente, executamos o BPE nos bytes individuais de texto codificado em UTF-8. Ou seja, pegamos uma representação Unicode de texto como uma série de pontos de código, codificamos em bytes usando UTF-8 e tratamos cada um desses bytes individuais como a entrada para o BPE. Assim, o BPE provavelmente começa redescoberto as sequências comuns de 2 bytes e 3 bytes que o UTF-8 usa para codificar vários pontos de código. Novamente, executar o BPE apenas dentro de palavras pré-segmentadas ajuda a evitar problemas. Como há apenas 256 valores possíveis para um byte, não haverá *tokens* desconhecidos, embora seja possível que o BPE aprenda algumas sequências UTF-8 ilegais através de limites de caracteres. Estas serão muito raras e podem ser eliminadas com um filtro.

2.5 Corpora

As palavras não aparecem do nada. Qualquer pedaço de texto que estudamos é produzido por um ou mais falantes ou escritores específicos, em um dialeto específico de uma língua específica, em um momento específico, em um lugar específico, para uma função específica.

AAEMAE

Talvez a dimensão mais importante de variação seja a língua. Os algoritmos de NLP são mais úteis quando se aplicam a muitos idiomas. O mundo tem 7097 idiomas na época desta escrita, de acordo com o catálogo online Ethnologue (Simons and Fennig, 2018). É importante testar algoritmos em mais de um idioma, e particularmente em idiomas com propriedades diferentes; em contraste, há uma tendência infeliz de os algoritmos de NLP serem desenvolvidos ou testados apenas em inglês (Bender, 2019). Mesmo quando os algoritmos são desenvolvidos além do inglês, eles tendem a ser desenvolvidos para os idiomas oficiais de grandes nações industrializadas (chinês, espanhol, japonês, alemão etc.), mas não queremos limitar as ferramentas apenas a esses poucos idiomas. Além disso, a maioria dos idiomas também tem múltiplas variedades, frequentemente faladas em diferentes regiões ou por diferentes grupos sociais. Assim, por exemplo, se estivermos processando texto que usa características do inglês afro-americano (AAE) ou do inglês vernáculo afro-americano (AAVE)—as variações do inglês que podem ser usadas por milhões de pessoas em comunidades afro-americanas (King 2020)—devemos usar ferramentas de NLP que funcionem com as características dessas variedades. 2.6 Expressões Regulares

expressão regular

Uma das ferramentas mais úteis para processamento de texto em ciência da computação é a expressão regular (ou regex), uma linguagem para especificar strings de texto. Regexes são usadas em toda linguagem de programação, em ferramentas de processamento de texto como Unix grep, e em editores como vim ou Emacs. E elas desempenham um papel importante na etapa de pré-tokenização para algoritmos de tokenização como BPE. Formalmente, uma expressão regular é uma notação algébrica para caracterizar um conjunto de strings. Praticamente, podemos usar uma regex para procurar uma string em um texto e para especificar como mudar a string, ambos são cruciais para a tokenização.

string

Usamos expressões regulares para procurar um padrão ... em uma string ..., que pode ser uma linha única ou um texto mais longo. Por exemplo, a função Python

re.search(pattern,string)

escaneia a string e retorna a primeira correspondência dentro dela para o padrão. Nos exemplos a seguir, geralmente destacamos a string exata que corresponde à expressão regular e mostramos apenas a primeira correspondência. Usaremos a sintaxe Python, expressando a regex como uma string bruta (com o prefixo bruto do Python r, delimitada por aspas duplas: r"regex"). 2.6.1 Disjunção de Caracteres: O Colchete

disjunção de caracteres

O tipo mais simples de expressão regular é uma sequência de caracteres simples. O padrão r"Buttercup" corresponde à substring Buttercup em qualquer string (como a string I’m called little Buttercup). Mas muitas vezes precisamos usar caracteres especiais. Por exemplo, podemos querer corresponder a algum caractere ou a outro. Por exemplo, as expressões regulares são geralmente sensíveis a maiúsculas e minúsculas: r"s" corresponde a um s minúsculo, mas não a um S maiúsculo. Para corresponder tanto a s quanto a S, podemos usar o operador de disjunção de caracteres /b«, os colchetes [ e ]. A string de caracteres dentro dos colchetes especifica uma disjunção de caracteres a serem correspondidos. Por exemplo, a Fig. 2.8 mostra que o padrão r"[mM]" corresponde a padrões contendo ou m ou M.

intervalo

A expressão regular r"[1234567890]" especifica qualquer dígito único. Isso pode ficar estranho (imagine digitar r"[ABCDEFGHIJKLMNOPQRSTUVWXYZ]" para significar uma letra maiúscula) então os colchetes também podem ser usados com um hífen (-) para especificar qualquer caractere em um intervalo. O padrão r"[2-5]" especifica qualquer um dos caracteres 2, 3, 4, ou 5. O padrão r"[b-g]" especifica um dos caracteres b, c, d, e, f, ou g. Alguns outros exemplos são mostrados na Fig. 2.9.

Os colchetes também podem ser usados para especificar o que um caractere único não pode ser, usando o acento circunflexo ˆ. Se o acento circunflexo ˆ for o primeiro símbolo após o colchete de abertura [, o padrão resultante é negado. Por exemplo, o padrão r"[â]" corresponde a qualquer caractere único (incluindo caracteres especiais) exceto a. Isso é verdade apenas quando o acento circunflexo é o primeiro símbolo após o colchete de abertura. Se ocorrer em qualquer outro lugar, geralmente significa um acento circunflexo; a Fig. 2.10 mostra alguns exemplos.

2.6.2 Contagem, Opcionalidade e Wildcards

Como podemos falar sobre elementos opcionais, como um s se quisermos corresponder akoala e a koalas? Não podemos usar os colchetes, porque embora eles nos permitam dizer “s ou S”, eles não nos permitem dizer “s ou nada”. Para isso usamos o ponto de interrogação r"?", que significa “o caractere precedente ou nada”. Assim r"colou?r" corresponde a color e a colour, e r"koalas?" corresponde a koala ou a koalas.

Há outra maneira de falar sobre elementos que podem ou não ocorrer. Considere a linguagem de certas ovelhas, que consiste em strings que se parecem com o seguinte:

baa! baaa! baaaa!

...

Kleene *

Esta linguagem de ovelhas consiste em strings com um b, seguidas por pelo menos dois (e arbitrariamente mais) a, seguidas por um ponto de exclamação. Para representar esta linguagem, usaremos um operador útil representado pelo asterisco ou *, chamado estrela de Kleene * (geralmente pronunciado “cleany star”). A estrela de Kleene significa “zero ou mais ocorrências do caractere ou expressão regular imediatamente anterior”. Assim, r"a*" significa “qualquer string de zero ou mais a.

O r"ba*" pode representar a língua das ovelhas? Ele corresponderá corretamente a ba ou baaaaaa, mas há um problema! Ele também corresponderá a b, sem a, ou ba com apenas um a. Isso ocorre porque o asterisco de Kleene significa “zero ou mais ocorrências”. Em vez disso, para a língua das ovelhas, queremos r"baaa*", significando b seguido por aa seguido por zero ou mais as adicionais. Padrões mais complexos também podem ser repetidos. Então, r"[ab]*" significa “zero ou mais as ou bs” (não “zero ou mais colchetes quadrados à direita”). Isso corresponderá a strings como aaaa ou ababab ou bbbb, bem como a string vazia. Para especificar um inteiro (uma string de dígitos), podemos usar r"[0-9][0-9]*". (Por que não é apenas r"[0-9]*"?)

Kleene +

Existe uma maneira ligeiramente mais curta de especificar “pelo menos um” de algum caractere: o Kleene +, que significa “uma ou mais ocorrências do caractere ou expressão regular imediatamente anterior”. Assim, r"[0-9]+" é a maneira normal de especificar “uma sequência de dígitos”, e também poderíamos especificar a língua das ovelhas como r"baa+!".

Além do asterisco de Kleene e do + de Kleene, também podemos usar números explícitos como contadores, envolvendo-os em chaves. O operador r"{3}" significa “exatamente 3 ocorrências do caractere ou expressão anterior”. Assim, r"ax{10}z" corresponderá a a seguido por exatamente 10 xs seguidos por z.

ponto

Um caractere especial importante é o ponto (r"."), uma expressão de curinga que corresponde a qualquer caractere único (exceto uma quebra de linha).

O curinga é frequentemente usado junto com o asterisco de Kleene para significar “qualquer string de caracteres”. Por exemplo, suponha que queremos encontrar qualquer linha em que uma palavra específica, por exemplo, rose, apareça duas vezes. Podemos especificar isso com a expressão regular r"rose.*rose", significando duas rosas, com uma sequência de zero ou mais caracteres (de qualquer tipo) entre elas. A Fig. 2.11 resume.

2.6.3 Âncoras e Limites

âncoras

Os Âncoras são caracteres especiais que ancoram expressões regulares em lugares específicos em uma string. As âncoras mais comuns são o acento circunflexo ˆ e o sinal de dólar $. O acento circunflexo ˆ corresponde ao início de uma linha. O padrão r"T̂he" corresponde à palavra The apenas no início de uma linha. Assim, o acento circunflexo ˆ tem três usos: corresponder ao início de uma linha, indicar uma negação dentro de colchetes e apenas significar um acento circunflexo. (Quais são

os contextos que permitem ao sistema saber qual função um dado acento circunflexo deve ter?) O sinal de dólar $ corresponde ao final de uma linha. Assim, o padrão ␣$ é um padrão útil para corresponder a um espaço no final de uma linha, e r"T̂he dog\.$" corresponde a uma linha que contém apenas a frase The dog. com um ponto final.

Note que temos que usar a barra invertida no exemplo anterior porque queremos que o . signifique “ponto” e não o curinga. Por contraste, a expressão regular r"T̂he dog.$" corresponderia a The dog. mas também a The dog! e The dogo. Como discutiremos abaixo, todos os caracteres especiais que definimos até agora (* + ? . [ ]) precisam ser escapados quando queremos usá-los literalmente.

Existem outros âncoras: \b corresponde a um limite de palavra, e \B corresponde a um não limite de palavra. Assim, r"\bthe\b" corresponde à palavra the mas não à palavra other. Uma “palavra” para os propósitos de uma regex é definida (com base nas palavras em linguagens de programação) como uma sequência de dígitos, sublinhados ou letras. Assim r"\b99\b" corresponderá à string 99 em There are 99 bottles of beer on the wall (porque 99 segue um espaço) mas não 99 em There are 299 bottles of beer on the wall (já que 99 segue um número). Mas corresponderá a 99 em $99 (já que 99 segue um cifrão ($), que não é um dígito, sublinhado ou letra).

Note que todos esses âncoras e operadores de limite correspondem tecnicamente à string vazia, o que significa que eles não consomem nenhum caractere da string. O acento circunflexo no padrão r"T̂he" corresponde ao início de "The" mas não avança realmente sobre o primeiro caractere T. E o padrão r"the\b the" corresponde a the the; \b está ciente do fato de que o espaço é um limite, mas corresponde à string vazia imediatamente antes do espaço, não ao espaço, para que o caractere de espaço esteja disponível para ser correspondido.

2.6.4 Disjunção, Agrupamento e Precedência

disjunção

Suponha que precisemos pesquisar textos sobre animais de estimação; talvez estejamos particularmente interessados em gatos e cachorros. Nesse caso, podemos querer pesquisar ou a string cat ou a string dog. Como não podemos usar colchetes para pesquisar “gato ou cachorro” (por que r"[catdog]" não faria a coisa certa?), precisamos de um novo operador, o operador disjunção, também chamado de símbolo pipe |. O padrão r"cat|dog" corresponde ou à string cat ou à string dog.

precedência

Às vezes precisamos usar este operador de disjunção no meio de uma sequência maior. Por exemplo, suponha que eu queira pesquisar menções de peixes de estimação. Como posso especificar tanto guppy quanto guppies? Não podemos simplesmente dizer r"guppy|ies", porque isso corresponderia apenas às strings guppy e ies. Isso ocorre porque sequências comoguppy têm precedência sobre o operador de disjunção |. Para fazer o operador de disjunção se aplicar apenas a um padrão específico, precisamos usar os operadores de parênteses ( e ). Envolver um padrão em parênteses faz com que ele aja como um único caractere para os propósitos de operadores vizinhos como o pipe | e o Kleene*. Assim, o padrão r"gupp(y|ies)" especificaria que queríamos que a disjunção se aplicasse apenas aos sufixos y e ies.

O operador de parênteses ( também é útil quando estamos usando contadores como o Kleene*. Ao contrário do operador |, o operador Kleene* se aplica por padrão apenas a um único caractere, não a uma sequência inteira. Suponha que queremos corresponder a instâncias repetidas de uma string. Talvez tenhamos uma linha que tenha rótulos de coluna do tipo Column 1 Column 2 Column 3. A expressão r"Column␣[0-9]+␣*" não corresponderá ao nosso significado pretendido de qualquer número de Colunas; em vez disso, corresponderá a uma única instância de Column seguida por qualquer número de espaços! O asterisco aqui se aplica apenas ao espaço ␣ que o precede, não a toda a sequência. Com os parênteses, poderíamos escrever a expressão r"(Column␣[0-9]+␣+)*" para corresponder à palavra Column, seguida por um número e espaços, o padrão inteiro repetido zero ou mais vezes.

precedência de operadores

guloso

Os padrões podem ser ambíguos de outra maneira. Considere a expressão r"[a-z]*" ao corresponder ao texto once upon a time. Como r"[a-z]*" corresponde a zero ou mais letras, esta expressão pode corresponder a nada, ou apenas à primeira letra o, on, onc, ou once. Nesses casos, as expressões regulares sempre correspondem à string maior que podem; dizemos que os padrões são greedy, expandindo-se para cobrir o máximo de uma string possível.

não-guloso*?+?

2.6.7 Substituições e Grupos de Captura

substituição

Um uso importante de expressões regulares é em substituições, onde queremos substituir uma string por outra. Expressões regulares podem nos ajudar a especificar a string a ser substituída, bem como a substituição. Em Python usamos a função re.sub() (funções similares existem em outras linguagens e ambientes).

re.sub(pattern, repl, string) recebe três argumentos: um pattern para procurar, um replacement para substituí-lo, e um string no qual fazer a busca e substituição. Poderíamos, por exemplo, mudar toda ocorrência de cherry para apricot em string:

re.sub(r"cherry", r"apricot", string)

Ou poderíamos converter para maiúsculas todas as ocorrências de um nome específico:

re.sub(r"janet", r"Janet", string)

Mais frequentemente, no entanto, a substituição depende de uma maneira mais complexa da string que correspondeu ao padrão /i». Por exemplo, suponha que temos um documento no qual todas as datas estão no formato dos EUA (mm/dd/yyyy) e queremos mudá-las para o formato usado na UE e em muitas outras regiões: (dd-mm-yyyy). O padrão /i»code r"\d{2}/\d{2}/\d{4}"/code» corresponderá a uma data. Mas como especificamos no replacement/i» que queremos trocar os valores de dia e mês?

grupo de captura

A ferramenta em expressão regular para isso é o grupo de captura .... Um grupo de captura usa parênteses para capturar (armazenar) os valores que encontramos na busca, para que possamos reutilizá-los na substituição. Colocamos um conjunto de parênteses ao redor da parte do padrão que queremos capturar, e ela será armazenada em um grupo numerado (os grupos são numerados da esquerda para a direita). Em seguida, no substituto, referimo-nos a esse grupo com um comando de número.

Considere a seguinte expressão:

re.sub(r"(\d{2})/(\d{2})/(\d{4})", r"\2-\1-\3", string)

Colocamos parênteses ( e ) em torno dos dois dígitos do mês, dos dois dígitos do dia e dos quatro dígitos do ano, armazenando assim os primeiros 2 dígitos no grupo 1, os segundos 2 dígitos no grupo 2 e os dígitos finais no grupo 3. Em seguida, na string repl, usamos os operadores number \1, \2 e \3 para nos referirmos ao primeiro, segundo e terceiro registros. O resultado seria uma string como

The date is 10/15/2011

e converta-a para

The date is 15-10-2011

Os grupos de captura podem ser úteis mesmo que não estejamos fazendo substituições. Por exemplo, podemos usá-los para encontrar repetições, algo que frequentemente precisamos no processamento de texto. Por exemplo, para encontrar uma palavra repetida em uma string, podemos usar este padrão que procura por uma palavra, a captura em um grupo e depois se refere a ela após espaços em branco:

r"\b([A-Za-z]+)\s+\1\b"

grupo de não-captura

Parênteses, assim, têm uma dupla função em expressões regulares; são usados para agrupar termos para especificar a ordem em que os operadores devem ser aplicados, e são usados para capturar a correspondência. Ocasionalmente, precisamos de parênteses para agrupar, mas não queremos capturar o padrão resultante. Nesse caso, usamos um grupo não capturador ..., que é especificado colocando os comandos especiais ?: após o parêntese de abertura, na forma (?: pattern ). Grupos não capturadores são geralmente usados quando estamos tentando capturar apenas parte de um padrão longo ou complexo. Talvez estejamos correspondendo a uma sequência de datas (\d\d/\d\d/\d\d\d\d) separadas por espaços e queremos extrair apenas a 15ª. Precisamos usar parênteses para usar o operador de contagem nos 14 primeiros, mas não queremos armazenar todas as informações inúteis. O padrão a seguir armazena apenas a 15ª data no grupo 1:

r"(?:\d\d/\d\d/\d\d\d\d\s+){14}(\d\d/\d\d/\d\d\d\d)" (2.17)

2.6.8 Asserções de Lookahead

Finalmente, haverá momentos em que precisamos prever o futuro: olhar para a frente no texto para ver se algum padrão corresponde, mas ainda não avançar o ponteiro que sempre mantemos no local em que estamos no texto, para que possamos então lidar com o padrão se ele ocorrer, mas se não ocorrer, podemos verificar outra coisa em vez disso.

lookaheadzero-largura

Estas asserções de lookahead utilizam a sintaxe (? que vimos na seção anterior para grupos de não-captura. O operador (?= pattern) é verdadeiro se pattern ocorrer, mas é zero-width, ou seja, o ponteiro de correspondência não avança, assim como vimos com âncoras e marcadores de limite como \b. O operador (?! pattern) só retorna verdadeiro se um padrão não corresponder, mas novamente é zero-width e não avança o ponteiro. O lookahead negativo é comumente usado quando estamos analisando algum padrão complexo, mas queremos excluir um caso especial. Por exemplo, suponha que queremos capturar a primeira palavra na linha, mas somente se ela não começar com a letra T. Podemos usar o lookahead negativo para fazer isso:

r"ˆ(?![tT])(\w+)\b" (2.18)

O primeiro lookahead negativo diz que a linha não deve começar com t ou T, mas corresponde à string vazia, sem mover o ponteiro de correspondência. Em seguida, o grupo de captura captura a primeira palavra.

2.7 Ferramentas Unix Simples para Tokenização de Palavras

Para o inglês, é possível fazer tokenização de palavras ingênua simples e computação de frequência em um único comando de linha de comando Unix. Como Church (1994) aponta, isso pode ser útil quando precisamos de informações rápidas sobre um corpus de texto. Usaremos alguns comandos Unix: tr, usado para mudar sistematicamente caracteres particulares na entrada; sort, que ordena as linhas de entrada em ordem alfabética; e uniq, que colapsa e conta linhas idênticas adjacentes.

Por exemplo, vamos começar com as ‘palavras completas’ de Shakespeare em um arquivo, sh.txt. Podemos usar tr para tokenizar as palavras mudando cada sequência de caracteres não alfabéticos para uma nova linha (’A-Za-z’ significa alfabético e a opção -c complementa (portanto, de alfabético para não-alfabético), então juntos isso seleciona cada caractere não alfabético, que o tr muda para uma nova linha. A opção -s (‘squeeze’) é usada para substituir o resultado de múltiplas mudanças consecutivas em uma única saída, de modo que uma série de caracteres não alfabéticos em sequência seria ‘squeezed’ em uma única nova linha):

tr -sc ’A-Za-z’ ’\n’ < sh.txt

A saída deste comando será:

THE SONNETS by William Shakespeare From fairest creatures ... [em português: Os Sonetos por William Shakespeare De criaturas mais belas...]

Agora que há uma palavra por linha, podemos ordenar as linhas e passá-las para uniq -c, que as colapsará e contará:

tr -sc ’A-Za-z’ ’\n’ < sh.txt | sort | uniq -c

com a seguinte saída:

1945 A 72 AARON 19 ABBESS 25 Aaron 6 Abate 1 Abates ...

Alternativamente, podemos converter todas as letras maiúsculas para minúsculas:

tr -sc ’A-Za-z’ ’\n’ < sh.txt | tr A-Z a-z | sort | uniq -c

cuja saída é

14725 a 97 aaron 1 abaissiez 10 abandon 2 abandoned 2 abase 1 abash 14 abate ...

Agora podemos ordenar novamente para encontrar as palavras frequentes. A opção -n para sort significa ordenar numericamente em vez de alfabeticamente, e a opção -r significa ordenar em ordem inversa (do maior para o menor):

tr -sc ’A-Za-z’ ’\n’ < sh.txt | tr A-Z a-z | sort | uniq -c | sort -n -r

Os resultados mostram que as palavras mais frequentes em Shakespeare, como em qualquer outro corpus, são as palavras de função curtas como artigos, pronomes, preposições:

27378 the 26084 and 22538 i 19771 to 17481 of 14725 a 13826 you ...

Ferramentas Unix desse tipo podem ser muito úteis na construção de estatísticas rápidas de contagem de palavras para qualquer corpus em inglês. Para algo mais complexo, geralmente recorremos aos algoritmos de tokenização mais sofisticados que discutimos acima.

2.8 Tokenização Baseada em Regras

Embora a tokenização baseada em dados, como BPE, seja a maneira mais comum de realizar a tokenização, também existem situações em que queremos restringir nossos tokens a serem palavras e não subpalavras. Isso pode ser útil se estivermos executando algoritmos de análise sintática para inglês, onde o analisador sintático pode precisar de palavras gramaticais como entrada. Ou pode ser útil para qualquer aplicação linguística onde temos alguma definição a priori do token que estamos interessados em estudar. Ou pode ser útil para aplicações de ciências sociais onde palavras ortográficas são domínios de estudo úteis.

Na tokenização baseada em regras, pré-definimos um padrão e implementamos regras para implementar esse tipo de tokenização. Vamos explorar isso para a tokenização de palavras em inglês.

Temos alguns desejos para o inglês. Frequentemente queremos separar a pontuação como um token separado; vírgulas são uma peça de informação útil para analisadores sintáticos, e pontos ajudam a indicar limites de frases. Mas muitas vezes queremos manter a pontuação que ocorre internamente na palavra, em exemplos como m.p.h., Ph.D., AT&T e cap’n. Caracteres especiais e números precisarão ser mantidos em preços ($45.55) e datas (01/02/06); não queremos segmentar esse preço em tokens separados de “45” e “55”. E existem URLs (https://www.stanford.edu), hashtags do Twitter (#nlproc) ou endereços de e-mail (someone@cs.colorado.edu).

As expressões numéricas introduzem complicações; além de aparecerem em limites de palavras, vírgulas aparecem dentro de números em inglês, a cada três dígitos: 555,500.50. A tokenização difere por idioma; idiomas como espanhol, francês e alemão, por exemplo, usam uma vírgula para marcar o ponto decimal e espaços (ou às vezes pontos) onde o inglês coloca vírgulas, por exemplo, 555 500,50.

clítico

Um tokenizer baseado em regras também pode ser usado para expandir contrações de clíticos marcadas por apóstrofos, convertendo what’re nos dois tokens what are, e we’re em we are. Um clítico é uma parte de uma palavra que não pode ficar sozinha e só pode ocorrer quando está anexada a outra palavra. Tais contrações ocorrem em outras línguas alfabéticas, incluindo pronomes franceses ( j’ai) e artigos ( l’homme).

Dependendo da aplicação, os algoritmos de tokenização também podem tokenizar expressões multi-palavra como New York ou rock ’n’ roll como um único token, o que requer um dicionário de expressões multi-palavra de algum tipo. A tokenização baseada em regras está assim intimamente ligada ao reconhecimento de entidade nomeada, a tarefa de detectar nomes, datas e organizações (Capítulo 18).

tokenização Penn Treebank

Um padrão de tokenização comumente usado é conhecido como padrão de tokenização Penn Treebank Penn Treebank tokenization, usado para os corpora analisados (treebanks) liberados pelo Linguistic Data Consortium (LDC), a fonte de muitos conjuntos de dados úteis. Este padrão separa clíticos (doesn’t se torna does mais n’t), mantém palavras com hífen juntas e separa toda a pontuação (para economizar espaço estamos mostrando espaços visíveis ‘ ’ entre os tokens, embora quebras de linha sejam uma saída mais comum):

Input: "The San Francisco-based restaurant," they said, "doesn’t charge $10". Output: " The San Francisco-based restaurant , " they said , " does n’t charge $ 10 " .

Na prática, como a tokenização é executada antes de qualquer outro processamento de linguagem, ela precisa ser muito rápida. Para tokenização de palavras baseada em regras, geralmente usamos algoritmos determinísticos baseados em expressões regulares compiladas em autômatos finitos eficientes. 2.8.1 Segmentação de Sentenças

segmentação de sentenças

A segmentação baseada em regras é comumente usada para outro tipo de processo de tokenização: a sentença. Sentence segmentation é uma etapa que pode ser aplicada opcionalmente no processamento de texto. É especialmente importante ao aplicar algoritmos de NLP a tarefas de detecção de estrutura, como estrutura de análise sintática.

A segmentação de sentenças depende da linguagem e do gênero. Os sinais mais úteis para segmentar um texto em sentenças em texto escrito em inglês tendem a ser a pontuação, como pontos, pontos de interrogação e pontos de exclamação. Pontos de interrogação e pontos de exclamação são marcadores relativamente inequívocos de limites de sentenças, e regras simples podem segmentar sentenças quando aparecem.

O caractere ponto “.”, por outro lado, é ambíguo entre um marcador de limite de sentença e um marcador de abreviações como Dr. ou Inc.. A sentença anterior que você acabou de ler mostrou um caso ainda mais complexo dessa ambiguidade, no qual o ponto final de Inc. marcou tanto uma abreviação quanto o marcador de limite de sentença. Por essa razão, a tokenização de sentenças e a tokenização de palavras podem ser tratadas conjuntamente.

Muitos métodos de tokenização de sentenças em inglês funcionam decidindo primeiro (muitas vezes com base em regras determinísticas, mas às vezes via aprendizado de máquina) se um ponto faz parte da palavra ou é um marcador de limite de sentença. Um dicionário de abreviações pode ajudar a determinar se o ponto faz parte de uma abreviação comumente usada; os dicionários podem ser construídos manualmente ou aprendidos por máquina (Kiss and Strunk, 2006), assim como o divisor de sentenças final. No kit de ferramentas Stanford CoreNLP (Manning et al., 2014), por exemplo, a divisão de sentenças é baseada em regras, uma consequência determinística da tokenização; uma sentença termina quando uma pontuação de fim de sentença (., !, ou ?) não está já agrupada com outros caracteres em um token (como para uma abreviação ou número), opcionalmente seguida por aspas ou colchetes finais adicionais.

2.9 Distância de Edição Mínima

Frequentemente precisamos de uma maneira de comparar o quão semelhantes são duas palavras ou strings. Como veremos em capítulos posteriores, isso surge mais comumente em tarefas como reconhecimento de fala automático ou tradução automática, onde queremos saber o quão semelhante a sequência de palavras é a alguma sequência de referência de palavras.

distância de edição mínima

A distância de edição nos dá uma maneira de quantificar essas intuições sobre similaridade de strings. Mais formalmente, a distância de edição mínima entre duas strings é definida como o número mínimo de operações de edição (operações como inserção, deleção, substituição) necessárias para transformar uma string em outra. Nesta seção, introduziremos a distância de edição para palavras únicas, mas o algoritmo se aplica igualmente a strings inteiras.

alinhamento

A lacuna entre intenção e execução, por exemplo, é 5 (deletar i, substituir e por n, substituir x por t, inserir c, substituir u por n). É muito mais fácil ver isso olhando para a visualização mais importante para distâncias de strings, um alinhamento entre as duas strings, mostrado na Fig. 2.17. Dados duas sequências, um alinhamento é uma correspondência entre substrings das duas sequências. Assim, dizemos que I alinha com a string vazia, N com E, e assim por diante. Abaixo das strings alinhadas há outra representação; uma série de símbolos expressando uma lista de operações operacional para converter a string superior na string inferior: d para deleção, s para substituição, i para inserção.

d s s i s

Também podemos atribuir um custo ou peso particular a cada uma dessas operações. A distância Levenshtein entre duas sequências é o fator de ponderação mais simples no qual cada uma das três operações tem um custo de 1 (Levenshtein, 1966)—assumimos que a substituição de uma letra por ela mesma, por exemplo, t por t, tem custo zero. A distância Levenshtein entre intenção e execução é 5. Levenshtein também propôs uma versão alternativa de sua métrica na qual cada inserção ou deleção tem um custo de 1 e as substituições não são permitidas. (Isso é equivalente a permitir a substituição, mas dando a cada substituição um custo de 2, já que qualquer substituição pode ser representada por uma inserção e uma deleção). Usando esta versão, a distância Levenshtein entre intenção e execução é 8.

2.9.1 O Algoritmo de Distância de Edição Mínima

Como encontramos a distância de edição mínima? Podemos pensar nisso como uma tarefa de busca, na qual estamos procurando o caminho mais curto—uma sequência de edições—de uma string

programação dinâmica

O espaço de todas as edições possíveis é enorme, então não podemos pesquisar de forma ingênua. No entanto, muitos caminhos de edição distintos acabarão no mesmo estado (string), então, em vez de recalcular todos esses caminhos, poderíamos apenas lembrar o caminho mais curto para um estado toda vez que o víamos. Podemos fazer isso usando programação dinâmica. Programação dinâmica é o nome de uma classe de algoritmos, introduzida pela primeira vez por Bellman (1957), que aplica um método baseado em tabela para resolver problemas combinando soluções de subproblemas. Alguns dos algoritmos mais comumente usados em processamento de linguagem natural utilizam programação dinâmica, como o algoritmo Viterbi (Capítulo 18) e o algoritmo CKY para análise sintática (Capítulo 19).

A intuição de um problema de programação dinâmica é que um problema grande pode ser resolvido combinando adequadamente as soluções de vários subproblemas. Considere o caminho mais curto de palavras transformadas que representa a distância de edição mínima entre as strings intenção e execução mostrado na Fig. 2.19.

Imaginamos uma string (talvez seja uma extensão exention) que está neste caminho ótimo (qualquer que seja). A intuição da programação dinâmica é que se exention estiver na lista de operações ótima, então a sequência ótima também deve incluir o caminho ótimo de intention até exention. Por quê? Se houvesse um caminho mais curto de intention até exention, poderíamos usá-lo em vez disso, resultando em um caminho geral mais curto, e a sequência ótima não seria ótima, levando a uma contradição.

O algoritmo de minimum edit distance foi nomeado por Wagner e Fischer (1974), mas descoberto independentemente por muitas pessoas (veja a seção Notas Históricas do Capítulo 18).

Vamos primeiro definir a distância de edição mínima entre duas strings. Dados dois strings, a string de origem X de comprimento n, e a string de destino Y de comprimento m, definiremos D[i, j] como a distância de edição entre X[1..i] e Y[1..j], ou seja, os primeiros i caracteres de X e os primeiros j caracteres de Y. A distância de edição entre X e Y é, portanto, D[n,m].

Usaremos programação dinâmica para computar D[n,m] de baixo para cima, combinando soluções para subproblemas. No caso base, com um substring de origem de comprimento i mas uma string de destino vazia, ir de i caracteres para 0 requer i exclusões. Com um substring de destino de comprimento j mas uma origem vazia, ir de 0 caracteres para j caracteres requer j inserções.
